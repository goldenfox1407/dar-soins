🏢 Niveau Business

1.1 — Qu'est-ce que Dar-Soins ?

Dar-Soins est une plateforme SaaS de santé connectant les patients au Maroc avec des infirmiers à domicile, supervisée par un back-office administratif. Il s'agit d'une solution globale combinant :

  • Un marketplace de soins à domicile (mise en relation patient ↔ infirmier par géolocalisation)
  • Un module ERP intégré (gestion des stocks, ventes, RH, finances)

1.2 — Modèle Économique

1.4 — Cycle de Vie d'une Intervention

Client commande un soin ↓ Géolocalisation → Recherche de l'infirmier le plus proche ↓ L'infirmier accepte ou refuse la mission ↓ Génération automatique d'un devis (tarif soin + frais de déplacement + TVA) ↓ Le client approuve le devis ↓ L'infirmier arrive sur site (pointage par photo / selfie) ↓ Enregistrement des constantes médicales + consommables utilisés ↓ Signature du patient + choix du mode de paiement ↓ Génération automatique de la facture finale (PDF)

📝 Niveau Code

3.1 — Structure Backend (26 Contrôleurs, 24 Modèles, 4 Services)

Contrôleurs orientés domaine métier

  • AuthController — inscription / connexion / profil avec création de profil selon le rôle
  • InterventionController — cycle complet : commande, affectation, devis, arrivée, clôture
  • ProduitController — CRUD avec mise en cache Redis via CacheService
  • FactureController — liste des factures + génération PDF (DomPDF)
  • EmployeController, TransactionFinanciereController, etc. — CRUD générique (scaffoldé)

Services (couche logique métier)

  • ServiceTarification — calcule les devis et factures (remise + déplacement + consommables + TVA)
  • ServiceAffectation — trouve l'infirmier disponible le plus proche
  • ServiceGeolocalisation — formule de Haversine pour le calcul de distance
  • CacheService — wrapper Redis pour la mise en cache
⚠️ Note importante

La plupart des modèles utilisent $guarded = [] (mass-assignment ouvert) — un risque de sécurité pour les contrôleurs ERP scaffoldés.

3.2 — Structure Frontend (~50 pages)

  • Pages publiques : Accueil, Services, À propos, FAQ, Contact, Connexion, Inscription
  • Espace Client : Commander un soin, consulter les interventions, télécharger les factures
  • Espace Infirmier : Missions (accepter/refuser), intervention active (constantes, consommables, signature, paiement), missions à venir (carte + pointage), historique
  • ERP Admin (~40 pages) : Interface de gestion complète avec thème sombre glassmorphism, navigation latérale, tables avec recherche, modales

3.3 — Points Forts

✅ Atouts du projet
  • Séparation claire des responsabilités (Contrôleurs → Services → Modèles)
  • API Resources pour une sortie JSON cohérente et structurée
  • Rate limiting et authentification dès le départ
  • Mise en cache Redis sur les listes de produits
  • Formule de Haversine pour le géocollaboration patient ↔ infirmier
  • Interface responsive avec Tailwind CSS + Framer Motion
  • Dockerisé pour le développement et la production
  • Bonne couverture de tests sur les flux principaux (Auth, Produits, Interventions)

🎯 Évaluation Synthétique

Dar-Soins est un projet ambitieux et bien architecturé qui combine un marketplace de soins de santé avec un ERP complet. Les fondations sont solides : authentification par rôles, géo-matching, logique de facturation, Docker, et CI/CD sont tous en place. Le frontend est soigné avec un design glassmorphism moderne.

Cependant, il existe des lacunes de sécurité critiques dans la couche ERP (mass-assignment, absence de vérification de rôle, aucune validation sur les contrôleurs scaffoldés) qui doivent être corrigées avant une utilisation en production. Les modules ERP semblent avoir été générés rapidement et nécessitent un durcissement.

5.2 — Recommandations Priorisées

🔴 Priorité 1 — Sécurité (avant production)
  1. Ajouter $fillable sur tous les modèles en remplacement de $guarded = []
  2. Ajouter un middleware de rôle (role:gestionnaire) sur toutes les routes ERP
  3. Ajouter des règles de validation ($request->validate([...])) dans tous les contrôleurs ERP
🟡 Priorité 2 — Nettoyage & Cohérence
  1. Supprimer les scripts temporaires (check_interventions.php, fill_*.php, etc.)
  2. Créer les fichiers docker-compose.yml et docker-compose.prod.yml manquants
  3. Corriger le test d'intervention (InterventionTest.php) pour qu'il corresponde à la réponse du contrôleur
  4. Utiliser une variable d'environnement pour l'URL de l'API dans api.js
🟢 Priorité 3 — Améliorations
  1. Ajouter des tests frontend (Vitest/Jest)
  2. Aligner .env.example sur PostgreSQL pour la cohérence avec la CI
  3. Corriger la sémantique de VentesList (ventes vs interventions)
  4. Envisager l'internationalisation (i18n) pour le frontend
